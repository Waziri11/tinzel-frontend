# Tinzel UI and UX audit — 1 November 2026

This report supports the local prototype redesign. It reviews the current local frontend and relevant server contracts, and reconciles the 30 October audit. The application itself is not changed by this work. The prototype records proposed behavior; it is not evidence of implemented accessibility, provider delivery, or production reliability.

All design records, names, emails and references use fictional samples. Existing brand imagery is supplied repository content. No real customer records, credentials, financial details or outbound messages are needed.

## Remaining shortcomings and redesign response

| Issue | Criticality | Description | Proposed solution |
|---|---|---|---|
| 1. Visual hierarchy varies between journeys | Medium | Landing, customer forms, staff tools and reader controls use independent inline sizing and spacing. Source: `src/App.jsx` and component styles. | Use one semantic token system, a consistent heading scale and reusable responsive layouts. |
| 2. Entry choices dominate the phone screen | Medium | `LandingHero.jsx` gives both options 240px height, heavy double borders and large italic labels. | Introduce an editorial cover-led home with concise primary and secondary actions and a short process overview. |
| 3. Brand treatment competes with content | Medium | Repeated gold borders, inlays, outlines and shadows occur on routine interactions. | Reserve dark ochre for primary actions; use quiet neutral surfaces and restrained decorative gold. |
| 4. Gold controls lack sufficient contrast | High | `theme/antdTheme.js` retains primary `#C5A059`; white labels on this fill are low contrast. CSS contains several competing gold values. | Use `#78571E` for meaningful action fills; retain the original gold for decoration. Verify every text/fill pair. |
| 5. Mobile headlines can still resist wrapping | Medium | `LandingHero.jsx` retains a `whiteSpace: nowrap` phrase and a 280px minimum card track. | Allow sentence wrapping and verify 320–430px widths with both languages. |
| 6. Blocking first-visit language screen is oversized | Low | Language entry occupies a full screen with large duplicated choice cards. | Keep a clear first-visit choice with compact accessible controls and persistent switching. |
| 7. Customer navigation is inconsistent | Medium | Home, catalogue and tracking render different sets of navigation controls; catalogue hides actions present elsewhere. | Use a consistent public header and a compact mobile menu. |
| 8. Inner footer exposes internal instructions | Low | `App.jsx` renders `footer.text`; translations include palette, gradients and emoji instructions. | Replace this with approved brand copy; do not invent contact or legal details. |
| 9. Form position is not fully addressable | Medium | Catalogue selection and dynamic form progress remain component-local state. | Define stable catalogue/order destinations and preserve Back/Forward behavior during implementation. |
| 10. Long questionnaires lack consistent progress framing | Medium | Dynamic sections, contact details, uploads and submission use a long changing layout. | Separate details, story, photos and review with visible progress and a saved-draft affordance. Preserve field semantics. |
| 11. Required errors need more precise placement | Medium | Several actions expose a single general error at page level. | Associate errors with fields, preserve other input, focus the first invalid field and add a concise error summary. |
| 12. Draft recovery needs clearer consequences | Medium | Browser-saved personal answers and upload recovery require distinct status and discard behavior. | Explain what is saved locally, provide resume/discard and distinguish storage failure from network failure. Expiry policy requires implementation work. |
| 13. Upload presentation is fragmented | Medium | Customer uploads, draft uploads, cover uploads and print files use different visual contracts and limits. | Reuse a transfer pattern with file-level progress, confirmation, failures and resumable states; show each actual limit. |
| 14. Successful transfers can crowd active failures | Medium | Large groups need attention focused on incomplete files rather than every completed item. | Collapse completed files and prioritize failed, retrying and confirming files. Never show 100% before server confirmation. |
| 15. Preview and archive preparation need different states | Medium | Photo thumbnails, folder ZIP preparation and original assets have independent readiness. | Use explicit preview-pending and ZIP-preparing states tied to the current order. |
| 16. Payment and submission need stronger distinction | High | A submitted order, payment instructions, payment verification and tracking access can appear like one completed action. | Show separate submission and payment statuses. Production starts only after verified payment. Use configured values only. |
| 17. Tracking access is duplicated | Medium | Follow-up modal and tracking portal each implement phone/code steps. | Use one consistent order lookup and OTP pattern across entry points. |
| 18. OTP recovery needs complete copy and affordances | Medium | Invalid codes, expiry, resends, delivery problems and service outages need distinct next actions. | Design each separately; preserve order context, show real cooldown data when supplied, and avoid invented success. |
| 19. Status visibility needs a clearer next action | Medium | Raw workflow vocabulary and long timelines require interpretation by customers. | Give each server status a customer-facing heading, current step, next action and appropriate released-proof access. |
| 20. Hold treatment needs visible continuity | Medium | A hold must not appear to reset the order. | Retain previous progress and display the reason and responsible next action. |
| 21. Proofing tools need clearer modes | Medium | Reading, text selection, image selection and area marking share a dense toolbar. | Distinguish the active mode and offer area marking when page metadata lacks selectable content. |
| 22. Proof comments need persistent save feedback | High | A failed annotation save must preserve its text and exact page target. | Provide saving, saved, failed, retry and discard states; keep the composer until persistence succeeds. |
| 23. Version context can be lost during review | High | Historical versions, private replacements and current review decisions have different permissions. | Keep version and release state visible. Make history read-only and prevent stale-version approval. |
| 24. Mobile reader controls need tighter grouping | Medium | Toolbars, page navigation and comments compete with the page on small screens. | Use wrapped tool controls, one page on mobile, a focused comment area and a clear fullscreen exit. |
| 25. Staff information density varies | Medium | Manager boards, queues, returns and user pages use different combinations of cards, lists and summaries. | Standardize compact searchable lists, restrained priority summaries and separate detail views. |
| 26. List state conventions are inconsistent | Medium | Empty lists, filtered zero results, load failures and refreshes can share weak or missing framing. | Give each a distinct message, preserved search context and useful next action. |
| 27. Staff dialogs need uniform keyboard behavior | High | Designer draft upload uses a custom dialog; a dialog role alone does not provide focus trapping, Escape handling or restoration. | Specify initial focus, Tab containment, safe Escape and focus return for every dialog and drawer. Verify in code later. |
| 28. Important actions need explicit consequences | High | Payment verification, draft release, print authorization, dispatch and closure change official workflow state. | Provide contextual confirmation with order/version references, prerequisites and outcomes. |
| 29. Assignment conflicts need a recovery screen | Medium | Availability can change between selection and submission. | Preserve the order, explain capacity changes and refresh eligible designers; server remains authoritative. |
| 30. Edition creation is visually overloaded | Medium | `FormBuilder.jsx` combines edition configuration, cover uploads, sections, questions and publication. | Group the editor into content/settings/preview and provide a dedicated contextual editor for every supported field type. |
| 31. Google import warnings need a clear review path | Medium | Imported content can contain unsupported items or missing media. | Keep imported editions unpublished, summarize warnings and link each to its editable section before publishing. |
| 32. User administration mixes access and delivery | Medium | Account details, workload, onboarding credentials and delivery attempts require different interpretations. | Present account status, assignment capacity and credential delivery as distinct sections. Preserve history and explain deactivation blockers. |
| 33. Message status needs stricter visual semantics | High | Queued, provider-accepted, delivered, failed and simulated attempts must not share a success appearance. | Use distinct badges and explanations, a sanitized attempt reference and eligible retry actions. |
| 34. Communications tools need clearer organization | Medium | Inbox, trigger settings, provider health and legacy diagnostics span overlapping panels. | Use one communication area with role-appropriate inbox, settings and health views. |
| 35. Kiswahili coverage remains incomplete | Medium | Staff menus and many labels in queues, form editing and notifications are hardcoded English. | Provide translated labels, validation, recovery and state copy throughout; allow longer text to reflow. |
| 36. Touch and focus affordances need consistency | Medium | Custom text actions, icons, rows and buttons do not share one target/focus contract. | Use at least 44px action targets, meaningful labels, non-color status cues and a visible focus ring. |
| 37. Session and network errors need separate presentation | High | Reconnection failure, expired authentication and denied permission require different next actions. | Keep retryable work visible; require sign-in only for invalid/expired sessions; provide role-specific access-denied states. |
| 38. No explicit page-not-found experience | Low | Unrecognized paths can fall back to the home view. | Add a designed not-found state with useful navigation and document the routing requirement. |

## Earlier findings rechecked

The following improvements exist in current source and must be retained: restored language preferences and document language, Back/Forward handlers, lazy role-level loading, catalogue load error/retry, designer search/status tabs/pagination, client session preservation for non-authentication errors, hold progress mapping and reduced-motion handling. These are not reported as still-missing functionality.

## Boundaries

Server enforcement, authentication/security remediation, transactional workflow changes, atomic capacity reservation, delivery receipts, rate limits, upload-storage infrastructure and production verification require implementation or operational work. A polished prototype state cannot provide those guarantees. This report does not repeat the earlier security findings as newly reproduced vulnerabilities.
